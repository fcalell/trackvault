## 2. Fixes ranked (stack cleaned vs cost to TrackVault)

1. **A. Player dock and `expo-audio` become an opt-in plugin** (largest clean-up: the only item that makes every native app pay for one app's feature).
   - New `@fcalell/plugin-native-player` (or `native-audio`): owns `expo-audio` as dependency, the `expo.slots.expoConfigPlugins` contribution (src/index.ts:510-515 moves there), `Player` (shell/player.tsx) and `lib/player` (phone host). Not in `nativeUi()`'s dependencies (index.ts:453-455 and package.json:101,143 lose `expo-audio`).
   - The Shell needs one generic seam, not an audio prop: a region above the tab bar fed by a slot-contributed component. Practical form: native-ui exports a tiny registry (`lib/dock`: `registerDock(component)`), the new plugin contributes it through `expo.slots.providers` (a provider that registers and renders children), and `Shell` renders the registered docks where `<Player/>` stands now (shell/index.tsx:107). That keeps the decision "the dock is above the routes, never in a screen" (docs/decisions/the-player-is-the-shells.md) and removes "no prop on the Shell" tension. Alternative without a registry: leave `Shell` as is but lazy-require `expo-audio` on first `play` and gate the dependency/config plugin on an option; weaker (still ships the Shell branch).
   - The decision doc already admits the trade-off "the sound needs a Shell"; it should be updated, and the store stays in ui-core.
   - Cost to TrackVault: add the plugin to apps/phone/stack.config.ts and package.json (also replaces the `link:../../../stack/apps/phone/node_modules/expo-audio` hack at apps/phone/package.json:25 with a proper `link:` to the plugin); change the import in 4 files (play.ts, index.tsx, playlist/[id].tsx; stack's apps/phone/player.tsx); no behaviour change. A new native build is needed either way.
2. **B. Move `server` out of native-ui to the plugin that owns the router (plugin-api)** and replace the `"auth.session"` string sniff with a slot. Cost: one config line in TV phone; stack gains web "client of another server" for free; native-ui drops about 100 lines of codegen and the auth-provider condition.
3. **C. `Sheet after`**: ask whether `children` (parts after the form are the default order?) can serve; low priority, shared with web; judge with the web auditor.
4. Everything else in 1b: leave.

## 3. What I would leave as is, and why

- Parity features (banner, offered, options text, empty selection, section read frames, window more, Stats cell frame, BarChart label, Form onChange/secret/description selection, kind rename): each is general, expressed through the existing model (data props, frames, acts), implemented through the same shared helpers as web, with no TrackVault noun.
- `SliderBase bare`/`said`: internal, neutral names, no public surface.
- The player store in ui-core and `lib/player` API (`windowQueue`, `headers`, async `track`): a media queue over a window read is a plausible pattern for any media app; its fault is only the unconditional mounting. Vocabulary (`Track`, `artist` in the lock screen mapping at shell/player.tsx) is music-shaped; a video or podcast app would need a different dock, which another plugin could provide once the seam exists.
- BarChart's `onLayout`: permitted by structure.md rule 7 for native.
