## R1 progress

Built (hub, migration `0004_wise_cannonball`):
- **Change log and undo.** Every write goes through `server/lib/changes.ts` (`applyPatches`: 500-row chunks, prepared statements that set only the columns that changed, each field in `changes` under a batch id; `flushTagWrites` puts a batch's tag fields into the files from the log itself, so a job resumed after a stop finishes). `batches` lists them; the History place pages them (window) and a batch opens beside the list as a table of `change` cells with Undo batch. The `undo` job puts back only the fields still at the batch's value (conflicts are skipped and counted), tags the files and moves moved or quarantined files back; the undo is a batch of its own.
- **Bulk acts on the library selection** (`choose` over the window read, `selector(libraryQuery)` resolved by `libraryWhere`): Edit tags (a sheet with a live preview table of before and after for the first 40 tracks, then the `edit` job), Apply rules, Organise (with the saved template), Find duplicates of these, Quarantine.
- **Taxonomy.** `genres`, `genreAliases`, `artistAliases`, `labelAliases`; genres seeded from core's seed taxonomy on first start. Genres (taxonomy, unknown values with the closest names, map in a click), Aliases (spellings that differ by case or punctuation grouped for a merge, aliases), library-wide Unify (`unify` job, preview then apply).
- **Custom tags.** `tags`, `trackTags`; the Custom tags place, the record's Tags list, the Edit tags sheet (add or take off), and a Tag filter with counts in the library.
- **Cleanup rules.** `rules` (core `Rule` as JSON, core's built-ins seeded off); the screen lists, switches, adds and edits (one action per rule, a Form with fields per action kind) and previews on the library (`rules` job in preview mode stores rows in `previews`, read in windows) before the apply job.
- **Organiser.** Template field with presets, `organise` job: preview (moves, numbered collisions, unchanged; a table of path before and after) and apply (core's `orderMoves`, cycles through a temporary name, `files.path` updated with each move so the scanner reads nothing again, emptied folders removed). Undo through History.
- **Quarantine.** `files.state = quarantined`, files moved under `<libraryRoot>/.quarantine/<batch>/`, tracks hidden from the library (issue bit 2048, which the list leaves out only while some exist); Quarantine place with restore, delete now, restore all and empty; `purge` runs every 6 hours for files older than `settings.quarantineDays` (30).
- **Health.** Jobs `integrity` (ffmpeg decode) and `bitrate` (spectral cutoff, core quality), each degrading to a "needs ffmpeg" result; issue bits `corrupt` (512) and `fakeBitrate` (1024) with partial indexes; the Issues place lists every issue with its count and a link into the filtered library.
- **Dedupe.** Jobs `fingerprint` (fpcalc, stored in `fingerprints`), `dedupe` (core `groupDuplicates`, keeper and reason from `pickKeeper`, stored in `dupeGroups` and `dupeMembers`; a dismissed group stays dismissed by its member-set key) and `merge` (core `mergePlan`: tags filled, custom tags moved, other files quarantined, one batch). The Duplicates place shows groups as bands, keeper first with its reason, Merge on the band, "Not duplicates" and "Keep this one instead" on a row.

Measured at 50k tracks on the build sandbox (`scripts/bench-queries.ts`, `scripts/bench-jobs.ts`): window query plus total 1.6 to 6 ms unfiltered, search and facets unchanged (after moving the list onto stack's `paginateWindow`); jobs over the whole library: rules preview 1.8 s, unify preview 0.8 s, organise preview 3.8 s, dedupe (exact and fuzzy) 1.5 s, edit of every track 7 s in the database (50k changes logged) plus the file writes, undo of that batch similar.

- **Wishlist.** `wishlist` table (key = folded artist|title|mix), the `wishlist` job applies core's retry schedule (`buildQueries` variant per attempt, `nextSearch` delays, give up at the end), downloads the best accepted candidate above the score when auto-download is on, else marks the want found; the service queues a run once a minute when a want is due (5 wants per run). - **Auto-tag.** Settings row: MusicBrainz user agent, AcoustID key, Discogs token, Beatport token, a switch per provider (Deezer needs no key), policy (fill empty or overwrite; overwrite never touches the title or artist it searched by), least confidence, days to remember answers, "tag new files in the inbox". `server/lib/autotag.ts` builds the providers the settings allow (one instance per job, so rate limits are shared), caches every response in `providerCache` (TTL, `ProviderCache` over a prepared statement), turns keys into Camelot and genres into taxonomy names before core `mergeCandidates` and `autotagPlan` (a genre the taxonomy does not know is dropped and counted). The `autotag` job over a selection (`selector(libraryQuery)`) stores `proposals` (field, before, after, source, source URL, confidence, other values); a rerun replaces the track's open proposals and does not propose again what was rejected. The Review place (Curate) is a Table of proposals in windows with a `change` cell, source, confidence; accept or reject per field (row act, more menu), for the chosen rows, all above a confidence, or all. Accepting queues `autotag-apply`: one batch (origin `autotag`, listed in History, undoable) for everything accepted, then the tag write; a field changed since the lookup goes `stale`; safe to run twice. The inbox pipeline's auto-tag step now runs the same plan into the item's proposed tags when the setting is on. "Auto-tag" is an act on the library selection, in the MCP tools, and on the track record.
- **Cover art.** `art` job: provider candidates and the Cover Art Archive through core `fetchBestCover`, `resizeCover` to 1000 px, embedded with `writeTrackFiles` (file hash and version follow), `hasArt` set and the "No artwork" issue cleared; tracks with art are skipped unless forced, a search that found nothing is not repeated for 30 days (`artChecks`). - **Analysis.** `analyse` job (queued after a scan that added tracks, per setting, or by an act): core `analyseTrack` on a niced ffmpeg, one track at a time, only the parts a track lacks, each result stored at once in `analysisResults` (value and confidence; `trackAnalysis` is the ANLZ blob table and is not reused), so a stop loses nothing and a rerun skips what is done. Empty BPM, key and energy tags are filled above the settings' confidence (batch origin `analysis`, written to the files); a tag with a value is never replaced and a track with Rekordbox's ANLZ files is not filled. `tracks.loudness` takes the LUFS. Energy and LUFS are library columns (sortable, LUFS hidden by default), energy is a filter, "Never played" is a filter; the record shows the analysis with its confidence.
- **Set builder.** The Set builder place: a draft set (`setDrafts`, one at a time), a library search to add from, "Start from a playlist", next-track suggestions after the last track (the library narrowed in SQL to compatible keys and the tempo range incl. half and double time, least recently played first, scored by core `nextTrackSuggestions` with the reasons; energy direction picker), the set as rows with each step's score and weak steps marked, reorder and remove, the energy curve, mix score, and Save as a playlist (manual, one batch). "Add to the set" is on the track record.
- **MCP.** `auth({ mcp: true })` (oauth tables in the migration), the `/connect/organization` and `/connect/consent` pages and the sign-in page resuming an authorization. `src/worker/mcp.ts` lists `agent.*` procedures written for a client: search, track, playlists, playlistTracks, stats, nextTracks (reads); addToPlaylist, createPlaylist (origin `mcp`, "Claude" in History), queueAutotag, queueAnalyse, queueArt (writes; tags are never edited directly, auto-tag results wait in Review).

## R5 progress: backups, offsite, hosting

Built (hub, migration `0008_certain_galactus`; pure parts in `packages/core/src/backup` and `src/s3`):
- **Database backups.** `backup` job (service `backup` queues it daily at `settings.backupHour`, hub local time; a hub off at the hour backs up at start; a failed attempt is not retried until the next hour): better-sqlite3's online backup page by page (4 MiB per turn of the event loop), settled to one file, `integrity_check` plus a row count per table, zstd (or gzip, none), and the packed file proved to unpack to the same SHA-256. `trackvault-<time>.sqlite.zst` with a `.json` sidecar (checksums, rows, verified, offsite) beside it in `settings.backupDir` (default `backups/` next to the database); the sidecar is not in the database so restoring an older database forgets nothing. Keep N daily / M weekly / K monthly (core `retained`, the newest good backup always stays; nothing is removed while none is good). `backup-verify` job rechecks a stored file (hash, unpack, integrity).
- **Restore.** `scripts/restore.ts` (local file; refuses while another process has the database open, detected by an exclusive lock attempt; unpacks and checks beside the target, moves the old database aside) and `scripts/restore-offsite.ts` (newest database backup, manifest, every audio file verified by audio hash, resumable by rerun).
- **Offsite.** Hand-written SigV4 (checked against botocore's signature for the same request) and an S3 client on node:http(s), no dependency: a dependency would only wrap `crypto.createHmac`, and the transport needs custom pacing for the bandwidth limit and Range resume that a fetch wrapper does not give. Works for AWS, R2, B2, MinIO (path-style or virtual-hosted). `offsite` job: database backups to `db/`, optionally every track to `audio/<audioHash>.<ext>` (single PUT or 16 MiB multipart parts with the upload id and parts kept in `offsite_uploads`, listed against the bucket on resume; 3 files at a time; speed limit shared by the whole job; skip by `offsite_objects` (key, file hash) and, when that table is lost, by listing the bucket and reading each object's stored file hash), then `manifest/latest.json.gz` (database backups, every file path with hashes). Remote database backups follow the keep policy; audio is never deleted from the bucket. Optional AES-256-GCM in 1 MiB chunks (file key by HKDF, chunk number as IV, last-chunk flag as additional data, so truncation and reordering fail; seekable, so multipart resumes) with a key the hub makes; the key lives in settings, so a copy kept elsewhere is what restores an encrypted bucket.
- **UI.** Settings: Backups and Offsite storage sections (secrets shown masked), Back up now, Test the connection, Send everything now, Show the key. The Backups place (System group): live rows of backup, check and offsite jobs from the jobs channel (progress, speed, bytes left), schedule and free space, local backups (size, tracks, checked state, offsite flag, Check now, Delete) and the bucket's database backups.
- **Hosting (D10).** `docs/deploy.md` with `deploy/` (systemd unit, env example, Caddyfile, Dockerfile, compose with slskd). D10 is settled as systemd first, Docker as the equivalent alternative.

Measured (build sandbox): a 50,000-track database (101 MB) backs up in 10 s end to end (copy, check, zstd to 37 MB, unpack proof) while the hub runs; the integrity check and the proof are synchronous or streaming work on the hub's thread, so the hub's other work waits during the check (about a second or two at this size). Production bundle built (`pnpm build`, 42 s) and started with `DB_FILE`, `AUTH_SECRET`, `APP_URL`.

Verified against moto (a Python S3 server, not MinIO: its binary download is blocked here): plain and encrypted multipart upload, a stopped upload continued from its saved parts, ranged and resumed download, list, delete, the bandwidth limit (3 MiB at 1 MiB/s took 2.8 s), wrong key and truncated file rejected, an end-to-end hub run (backup, then offsite of 5 files including a 46 MB encrypted multipart object, manifest), and `restore-offsite.ts` into an empty box with files byte-identical.

Left unverified: a real S3, R2 or B2 (virtual-hosted style, R2's region `auto`, B2's limits), systemd, Caddy and Docker (files written, not run), a very large first library upload, the screens' pointer paths. The Backups place does not restore from the UI: a restore replaces the database under a running hub, so it stays a script run with the hub stopped.

## Adopting stack's phone and deploy changes

Phone (`apps/phone`): now a client-only app. `stack.config.ts` is `expo({ scheme: "trackvault" })` and `nativeUi({ theme, server: "../hub" })`; the node/db/auth/api plugins, `src/schema`, `src/worker`, the worker tsconfig and the generated worker are gone. `lib/api.ts` imports `AppRouter` from `.stack/server` and builds `createClient({ url: () => ..., headers: async () => ... })` (address and device key read on every request; before the key, the sign-in session's cookie); `stack generate` copies the hub's schema in, so writes invalidate by the entities the hub names and the invalidate-all workaround (`lib/refresh.ts`) is deleted; `queryClient.clear()` runs in `lib/hub.ts` whenever the hub or the key changes. The "Heard in a club" sheet and the track record's "Add to a playlist" are `Form`s over `wishlist.add` and `playlists.add` (`sheetOf` from `lib/act`), no hand-built sheet or open flag remains.
Sign-in (`lib/sign-in.tsx`): hub address, then email code or device key. The code path uses `useAuthClient()` (the auto-mounted `AuthProvider` over `src/lib/auth.ts`, `baseURL: () => hub().url ?? ...`) with the hub's `auth({ expo: { scheme: "trackvault" } })`; once signed in it trades the session for a device key of this phone (`auth.devices.create` through the shared client, whose async headers carry the session cookie), signs the session out and keeps only the key, so the API and the player carry one credential.
Audio: `expo-audio` (a `link:` like the other expo modules). Library and playlist rows have a Play act (`lib/rows.ts`, `lib/play.ts`: `player.play(track, windowQueue(...))` over the window read, so Next and Previous follow the list's order and filter) and the track record a Play action; the playing row shows a speaker. The hub's `media.url` became `media.urls` (many ids, one request): the dock's cover and the lock screen's are fetched without headers, so file and `/media/<id>/art` carry a signed token; `windowQueue`'s `track` is async, so each row signs itself as its page loads (the ids of a page share one `media.urls` request, `lib/play.ts`).
